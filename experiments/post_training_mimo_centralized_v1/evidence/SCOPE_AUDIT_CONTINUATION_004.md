## Native collector versus full trainer

**Implementing source code and executing it are different gates.** Nothing found
in the research protocol makes writing a bounded collector physically dependent
on measured E0. Such implementation can be useful preparation if narrowly scoped:
one unchanged-source attempt per frozen open DEV row, exact input/output identity,
complete token/EOS/stop/resource/cost accounting, immutable failure receipts and a
concrete capture verifier. A prospective amendment should state its allowed scope.
CPU/fake-transport tests would establish only code mechanics. Missing E0 or
numerical budgets must stop before native imports/load; fixtures and arbitrary
callbacks cannot produce native-qualified receipts.

**Actual collection and qualified capture are E0-dependent.** The language design
requires qualified current runtime and tokenizer/termination semantics, semantic
bank review, grader calibration and frozen budgets before baseline calls.
`evidence/LANGUAGE_DEV_DESIGN.md` explicitly leaves numerical wall/GPU ceilings
unset pending measured E0 throughput. The 2048/4096 sentinel separately requires
the registered zero-update extension after E0. `configs/LONG_CONTEXT_SENTINEL_PROPOSAL.json`
has bounded profile counts, but its runtime portion remains unaccepted and
unmeasured; AMENDMENT_004 accepted its data-construction portion only. No apparent
collector completeness should erase these dependencies.

**Recommendation: do not prioritize a full runnable E1 trainer before E0.** This
is a sequencing recommendation, not a claim that trainer code cannot be written.
The current schedule/cursor work already resolves independent ordering and dose
choices. Exact native load/tying, numerical parity, gradients, optimizer precision,
save/reload/resume and actual resource peaks have not passed once in this campaign.
A full executor would consume those unmeasured assumptions and still could not
launch; language evaluation and long-context qualification would also remain
missing. Complete the candidate language inputs first, and, if another bounded
implementation task is needed, prefer the narrower source collector over the full
optimizer/checkpoint executor. Once E0 passes, bind the measured runtime and
budgets before implementing or qualifying the remaining actual execution path.

Do not refactor the E0 qualifier merely to make code appear reusable: changing its
critical source requires renewed binding/qualification. `scripts/e1_gates.py`
checks committed and current native source hashes, so a mechanics receipt cannot
silently qualify a subsequently changed loader or helper.
