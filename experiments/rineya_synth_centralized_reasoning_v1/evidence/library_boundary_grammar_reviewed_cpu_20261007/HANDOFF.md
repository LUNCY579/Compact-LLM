# Finite library expectation inputs

LIBRARY_EXPECTATION_INPUTS001.json joins the 8,714-file tensor byte candidate,
selected provider source, and actual observer009 inventory. The two observer009
initial snapshots agree on 35 paths. Those paths are registered as a future
tensor-program expectation, not proof of its current baseline. The expectation
must be checked in the future program; a mismatch remains a failure.

The static candidate contains 224 exact executable/DLL/PYD identities in 17
search directories, excluding the observer binary from dependent-library roles.
It records 37 byte-selected torch/lib DLL leaves and 48 potential unpreloaded
extensions. Torch __init__ source explicitly loads torch/lib *.dll in its Windows
_load_dll_libraries function and attempts fixed VC runtime names. Its environment,
optional directories, dependency effects and later Python extension imports can
change exact per-boundary effects and order. These source facts are not observed
transitions. No import of Torch, ctypes, framework, provider or DLL occurred.

The selected reviewed policy requires exact create/exec new-library lists for
each extension, exact directly loaded framework libraries after nested guard
acknowledgements, and exact initial set equality. Existing library policy/plan
tests use inert synthetic DLLs. They do not provide a recorded Torch import
order or expected native effects. Consequently extension_transitions,
framework_transition and library_boundary_plan remain null in this artifact,
and all native qualification/launch/authority fields remain false. It is an
input candidate, not a valid executable enforced-boundary policy.

Current ordering bars are in prefix_tensor_contract.library_boundary_plan and
prefix_library_evidence.selection/validate_observed_packet. The latter compares
each emitted enter to the next externally supplied id/parent/name row and
requires the complete registered list on successful terminal replay.

An optional finite registration amendment could replace only predeclared order
with a source-bound grammar: one framework root, finite selected extension paths,
at most one create and one exec per extension, exec after returned create,
sequential emitted IDs, strict LIFO current-stack parents and original depth/event
bounds. Exact expected library additions, identity conservation, snapshots,
events, cleanup, source pins, resource/numerical checks and closed native gates
would remain. Required extension dose must be independently registered. The
auditor would validate actual raw topology under that grammar, rather than trust
producer claims. This alternative is a review proposal only; no policy changed.

Even that amendment needs concrete exact per-extension and framework effect
expectations. A union of all selected DLLs is not an acceptable substitute for
exact effects. Root must choose the finite source-derived registration or an
explicitly authorized qualification step before a runnable tensor packet.
