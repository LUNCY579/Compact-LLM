## A: a real pinned receipt conflict under an unconfirmed cost classification

The exact code supports the mechanical part ofA. Library3 publishes its worker-
interval native_outcome_observation. OperationsStore.write_receipt460–485 fixes
one kind/key filename and refuses changed existing bytes; verify_receipt487–505
checks that identity; reconcile429–430 requires elapsed_native_seconds equal to
the proposed actual_native_seconds. Substituting a different duration/name,
overwriting the receipt or silently diverting canonical accounting is not allowed.

Consequently **if** this proposal requires the full t0-through-observer/accounting
interval to be the same native-cost number, its narrower existing receipt cannot
represent that interval under the stated fixed API. That is a genuine conflict
for the selected design, not an executed failure or a reason to repair canonical
accounting here.

The broader premise remains unresolved: original native-worker-hour/qualification
charging is not automatically identical to every source/construction/CPU observer
cost. The repository has distinguished CPU fixture/source/artifact/backup costs
from native consumption while preserving their visibility. This does **not**
authorize classifying native qualification or failures as free CPU work. Before
claimingA prevents every eligible integration, supply an authoritative interval/
activity cost map: what is governed native work, what is separate measured CPU
orchestration/assessment, what belongs to the reservation, and how every required
qualification/failure cost remains accounted without double-counting or omission.

If that map identifies required native costs beyond the immutable receipt with
no permitted existing accounting representation, retain a concrete fixed-API
cost blocker. Do not erase it by labeling the observer free, clipping overruns,
adding a second admitted key or changing the source. The current document has
not established that cost map sufficiently to prove the broader claim.

## B: valid for the chosen combined endpoint, not a platform impossibility

The code supports the stated ordering concern: reconcile samples finished_at
before UPDATE/event and transaction completion, offers no absolute-deadline commit
primitive and rejects conflicting terminal outcomes. A precommit sample cannot
prove later durable commit completed beforeD; a kill during COMMIT does not prove
rollback. With010's chosen **tE including all observer publication and canonical
commit before the sameD**, early immutable SUCCEEDED/late publication is a real
unresolved design issue.

But scope010 describes an unchanged10s **caller** bound and precisely bounded
observer validation/reconciliation with distinct clocks. It does not by itself
require every retrospective observer/ledger publication to be part of caller
execution. A bounded later reconciliation of a caller whose complete required
work was actually observed within10s is not automatically late native success.
The ledger commit timestamp is not itself the caller's elapsed completion proof.
This distinction permits no caller execution past10s, success from a pre-write
caller sample or cost-free/unbounded observer epilogue.

The proposal selects a stronger combined endpoint and then rejects it for lacking
an atomic commit-before-deadline primitive. That conditional rejection must not
be promoted into an all-platform or all-protocol impossibility. The earlier OPS
assessment's warning against moving an existing required endpoint outside10s is
a prospective constraint, not independent proof that the owner's worker allowance
universally includes every retrospective certificate. Preserve that wording and
the disagreement; clarify the exact timing/cost contract before further work.

## Genuine remaining readiness gaps

One broker holding caller/UV objects from creation is a concrete direction, but
atomic birth containment, handle duplication/RPC acknowledgement, caller loss,
observer loss and combined resource enforcement are all unimplemented/unqualified.
The proposal correctly refuses inferred orphan clearance. Selected files do not
prove an actual Windows birth-containment primitive unavailable; absence of that
proof is a readiness gap, not platform impossibility. No generic supervisor or
new code is prescribed by this review.

Required actual role/clean-commit/runtime/physical UV/controller DLL/search-root/
loader/trust/current-root/host DB/admission/lease/fence/request/worker/outcome
bindings remain symbolic. Immutable library3 in-memory retention does not discharge
them. Native interval receipts, complete caller artifacts, observer attestations
and their timing meanings must be separated without inventing ownership or early
success. Independent threads do not make blocked OS/fsync/SQLite calls bounded.

## Minimal restart condition, design-only

One prospectively registered finite clarification of this same proposal may be
useful, preserving all010 bytes/reasons and fixed APIs. It must deliver:

- One authoritative activity/interval cost map separating native worker and
  qualification/failure charging from separately measured source/CPU observer

- One exact10s caller endpoint including its required preparation, reservation,

  one separately finite observer assessment endpoint with explicit time/cost and

  not a timestamp before caller publication. Explain whether existing receipt

  preserve that specific technical blocker without API or library repair.
- Exact broker-held ownership requirements and finite caller/observer-loss,
  blocked-publication, missing-exit/resource and cost-mismatch falsifiers, all
  still design requirements rather than actual OS qualification.
