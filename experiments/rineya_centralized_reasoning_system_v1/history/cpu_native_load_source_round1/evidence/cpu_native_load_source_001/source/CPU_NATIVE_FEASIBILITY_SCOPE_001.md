## Verdict

A separately registered exact-checkpoint **CPU** path is scientifically legitimate
in principle under standing human direction `479b6c52`, provided its distinct
device envelope is explicit and every unchanged gate applicable to it is met.
It cannot be implemented by passing a CPU flag through the quarantined CUDA
reader/native source, dropping the GPU floor from that contract, or copying an
old approval. CPU qualification would be a separate result; it would not qualify
GPU execution or resolve GPU-specific historical numerical failures.

The files do **not** presently establish CPU fit or an eligible CPU launch. The
first useful measurement is a separately reviewed, preregistered, one-attempt
CPU **load-only** diagnostic under the original 2 GiB process-tree RSS cap,
before any four-forward experiment or reader qualification. If independent
source/resource review cannot justify that cap before launch, stop at the
resource feasibility blocker. More free system RAM does not authorize raising
the worker cap. This audit proposes no resource-policy amendment.

## Finite first resolving question

**Can the same canonical BF16 Titan checkpoint and pinned runtime complete one
CPU construction/streamed load, exact tie/count/per-tensor byte verification and
owned-Job exit within 2 GiB whole-tree RSS, with no CUDA API/context activity?**

Suggested preregistration: new CPU-specific contract and unique terminal key;
one model construction and one checkpoint load; 310 bounded tensor-copy spans;
zero forwards, generation, tokenizer loads, optimizer/teacher calls, training or
evaluation-bank reads; one attempt, no retry; wall <=120 s and native accounting
from dispatch through verified owned-tree exit. This is a stricter finite ceiling
than the original 600 s. The coordinator must freeze exact call counts, CPU
thread count (at most the original two), sample age <=5 s, resource stages,
reservation and abort/finalization semantics before approval. A failure is a
terminal feasibility observation, not permission to increase limits.

Measure import, construction, each bounded copy stage, loaded verification and
exit; retain OS whole-tree RSS/working-set peak and per-stage host/disk/time,
exact owned PID/creation/path/hash/Job witnesses, durable attempt/return journal,
asset/source/runtime bindings, CUDA participation evidence and accounting.
WindowsJob kill-on-close/no-breakaway, suspended launcher assignment before
resume, verified exact Job members before GO and during supervision, bounded
polling, owned-only termination, and verified empty-Job exit remain required.
Where available, enforce the registered memory ceiling with the Job as well as
the watchdog; Job committed-memory limits and RSS are different quantities and
must not be mislabeled. Both relevant limits must be recorded and tested.

CPU activity on a CUDA-enabled torch build is possible in principle; the pinned
runtime is torch2.10.0+cu126, Python3.11.15, transformers4.57.1,
safetensors0.7.0, tokenizers0.22.2 and psutil7.2.2. Retain these identities.
Setting `CUDA_VISIBLE_DEVICES` empty is defense in depth, not proof. The new
reviewed execution graph must construct and operate explicitly on `cpu`, avoid
all CUDA availability/device/synchronization/memory/RNG calls and CUDA backend
mutations, verify every model tensor is CPU BF16, and reject a GPU participation
observation or unexplained CUDA initialization. Torch imports can include CUDA
Python modules/DLLs on this build; report the precise observed distinction
between imported library and initialized device activity. Do not claim that
environment variables or a CPU device string alone establish isolation.

The existing stream loader uses one 2 MiB CPU buffer and generic target copies;
its documentation/receipt currently assert GPU copies and no CPU model. A
CPU-specific reviewed adapter must truthfully report CPU model allocation and
blocking CPU copies, retain strict tensor spans/dtypes/tie/count/hash validation,
and avoid a full second state-dict or checkpoint clone. No shared loader source
is changed by this advisory.
