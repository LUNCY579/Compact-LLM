# Cycle 002 registry requirements and evidence

The previous turn made concrete progress: a reviewed research pilot and its
exhaustive verifier/controller evidence exist. This cycle must improve source,
parent and structural integrity rather than regenerate the same rows.

## Boundaries

Existing foundry scripts/config and the pilot-v3 release remain unchanged. New
tools and evidence live in registry_tools, registry snapshots and this cycle's
folder. The active experiment and all sibling datasets remain read-only. No model,
paid API, source-code execution from legacy corpora, or reserved evaluation access.

Source intake reads explicit TRAIN paths, not a manifest's broadly named list.
Some IFC documentation labels DEV and TEST files as training_data_files. A
source-bundle/shard is a container; it is not necessarily the semantic grouping
unit. A document/revision family, conversational thread, repository family or
generated world is grouped by origin before rendering and target generation.

## Required registry behavior

1. Stable canonical construction-specification identities, independently of row
   IDs, release labels, entity aliases or file locations.
2. Prospective source/structure/parent reservations committed before rendering,
   solving, difficulty scoring or actor rows. Existing pilot-v3 registration is
   retrospective, explicitly labeled; importing it cannot rewrite its history.
3. Immutable ancestry, role inheritance and source-revision family assignments.
   Declared rewordings/renamings/length siblings/counterfactuals retain their
   canonical parent. Unknown undeclared semantic equivalence remains a limit.
4. Independent instance and structural identities. Sharing a structural cluster
   across TRAIN/DEV can be allowed for exposed instance development, but must be
   disclosed and cannot support unseen-structure evaluation claims.
5. Separate content-family sources from common producer code. A generator may
   produce independent worlds for multiple roles; a single content/revision
   family cannot be relabeled across roles.
6. Exact, normalized, lexical-token and native-token identities with explicitly
   different fingerprint types and scope. No character/word proxy is native length.
7. Idempotent byte-identical release reuse without counting new independent
   parents. Same identity with different immutable contents is a conflict.
8. Hash-chained immutable snapshots, exclusive write coordination, complete
   validation before commit and no partial mutation after a conflict.
9. Typed metadata and adversarial tests for duplicate keys/IDs, Boolean/integer
   confusion, bad hashes, role reassignment, source laundering and interrupted
   transactions. Local byte identities do not authenticate a malicious writer.
10. Explicit source-rights/admission and historical exclusion coverage. Known
    exclusions do not prove general semantic or pretraining decontamination.

## First scoped active/structure audit

The separate public-pilot fingerprint audit processed all72 authorized pilot
worlds. It found72 distinct exact active specifications and72 scoped normalized
instances, but30 structural signatures and14 shared signatures spanning roles.
Archive records, note text and record IDs do not establish new active-task
novelty. Limited item/account normalization catches the supported renaming cases.

Graph isomorphism is a structural fingerprint only: the lexicographically least
answer depends on names, so renaming cannot be falsely treated as identical answer
semantics. Quoted instruction attacks remain part of hierarchy stimulus identity.
Five executed adversarial controls validate these interpretation boundaries.
This audit covers the original pilot only and no legacy, closed-bank or pretraining
comparison. It does not certify broad semantic novelty.

## Next mechanism design gate

The next pilot must increase necessary evidence and reasoning horizon. It should
measure active fact/rule counts, distributed dependencies, stage counterfactuals,
answer-sensitive evidence interventions and missing/conflicting-evidence cases.
Adding clearly irrelevant archives or changing names does not satisfy that goal.

Reserve fresh structures for exposed DEV exploration while keeping all siblings
and source ancestry in one role. Actual structural variation must change inference
graphs/rules, not just prose labels. No new mechanism is accepted solely because
its generator and copied oracle agree.
